\section{Introduction}\label{sec:intro}
Computation draws electricity, and electricity carries a carbon footprint
that depends on where and how it is generated~\cite{lannelongue2021}. On a
shared high-performance computing (HPC) cluster, a user does not choose the
hardware a job draws on: a scheduler, here Slurm, grants an allocation of nodes,
cores and memory for a walltime, and the hardware is attributed to the job for
that time whether the program uses it or not.

The object of this study is one such job. It counts the exact canonical
31-mers of 5\,000\,000 sequencing reads of a bacterium, \emph{Mycobacterium
abscessus} (FASTA records counted on 19~October~2026), with
\texttt{kc-py1.py}, a single-threaded Python counter written for
teaching~\cite{kmercnt}. A $k$-mer is a substring of length $k$ of a DNA
sequence. Counting them is a common first step in genome analysis. The job runs
on the Aion cluster of the University of Luxembourg, and holds one 128-core node
exclusively while its program uses one core.

The footprint of this job is invisible to its user. Slurm returns no energy
figure for it (Section~\ref{sec:lci}), so the user sees a walltime and an exit
code, and nothing that shows what the run costs the climate. The allocation
shape, more than the program, may decide that cost. An optimisation guided by an
AI coding agent also has a cost of its own: the AI assistance and the test runs
it requires. It is worth doing only if the savings per run repay that cost
within the life of the job.

This paper answers the following research question: \emph{what is the GWP100
carbon footprint of one run of an exact 31-mer counting job that holds an
exclusive Aion node, which resource of that allocation carries it, and how many
runs does an AI-assisted optimisation of that resource need to pay back its own
footprint?} The first two parts concern one particular instance; the third
concerns a means~\cite{shaw2003}.

The contribution of this version is the baseline. It is a footprint per run
that rests on CPU-package energy counters read by an ordinary user, because the
scheduler's own energy fields are empty. It is completed by a declared model of
memory power, a proxy power usage effectiveness and an allocated share of
hardware production. Each figure is traceable to a measured value, a cited
factor or a labelled assumption, and the scripts that recompute them are kept
with the job.

Section~II positions the study. Section~\ref{sec:goalscope} defines the job,
the functional unit and the boundary. Section~\ref{sec:lci} inventories the
measured flows. Section~\ref{sec:lcia} converts them into gCO\textsubscript{2}e
per run, Section~\ref{sec:interpretation} interprets that figure, and
Section~\ref{sec:reporting} names its hotspots. Section~\ref{sec:optimisation}
attacks those hotspots, and Section~\ref{sec:payback} computes the carbon
payback. Section~\ref{sec:threats} lists the threats to validity.

\section{Life Cycle Assessment}
\guidance{The five subsections below follow Session 3 with respect to

\subsection{Goal and scope definition}\label{sec:goalscope}
The goal and scope definition fixes what is studied, the functional unit every
later figure refers to, the boundary of the system and the method that turns
inventory flows into an impact~\cite{iso14040,iso14044}.

\emph{Goal.} This study quantifies the carbon footprint of one execution of a
baseline 31-mer counting job. That footprint is the reference against which
the AI-assisted optimisation of Section~\ref{sec:optimisation} and its carbon
payback in Section~\ref{sec:payback} are measured.

\emph{The job.} The code is \texttt{kc-py1.py} from the public repository
\texttt{lh3/kmer-cnt}~\cite{kmercnt}, frozen at commit
\texttt{e2574719cfb7\allowbreak 84915d80eb58\allowbreak 28e78dfae4cf\allowbreak dd7b}.
It is a single-threaded Python~3 program. It reads FASTA from standard input and
counts every canonical 31-mer, the lexicographically smaller of a 31-mer and its
reverse complement. It skips any 31-mer that contains \texttt{N}. It prints a
histogram with 255 lines, one per count from 1 to 255, and pools every count
above 255 into the last line. The input is
\texttt{M\_abscessus\_HiSeq\_10M.fa.gz} from the repository's v0.1
release~\cite{kmercnt}: 187\,693\,955~bytes, SHA-256
\texttt{dd2ef49aebab\allowbreak fed1574b55fd\allowbreak 002025f29b2f\allowbreak da88c70b2095\allowbreak f5e1b3a822ce\allowbreak e736}.
It is decompressed on the fly by \texttt{gzip}. The program upper-cases only the
last record of its input. No sequence line of this input holds a lower-case
base (checked on 28~September~2026), so this does not affect the result. The job
is submitted with the Slurm script \texttt{run-baseline.sh} of the project
repository at commit
\texttt{253d93ec726b\allowbreak 82670c8f4b84\allowbreak da20e9528c9a\allowbreak 59ef}.
Every run writes the same 1\,972-byte histogram, SHA-256
\texttt{06a32de77200\allowbreak 121a397050e0\allowbreak 15a257953dc9\allowbreak 56b7854027a1\allowbreak ed73b15afc12\allowbreak bf42}.

\emph{The machine.} The job runs on the Aion cluster of the University of
Luxembourg HPC platform, partition \texttt{batch}, QoS \texttt{normal}, on the
regular compute node \texttt{aion-0127}. An Aion node holds two AMD EPYC~7H12
processors of 64~cores each, 256~GB of DDR4 memory, a 480~GB local SSD and one
HDR100 InfiniBand port~\cite{ulhpcaion}. The loaded modules are
\texttt{env/release/default} and \texttt{lang/Python/3.11.5-GCCcore-13.2.0}
(Python~3.11.5), as recorded in every run's log.

\emph{The allocation.} Each run holds one node exclusively: one task,
128~cores, all the memory Slurm can reserve on the node
(\texttt{-{}-mem=0}, recorded as 224\,000~MiB) and a walltime limit of
30~minutes. The program uses one of those cores. The node is reserved
exclusively so that no other job shares it. As a consequence, the whole node,
not one core, is attributed to the job.

\emph{The user.} The job is submitted with \texttt{sbatch} from an Aion login
node by the author, through a standard student account.

\emph{How many runs.} The functional unit is one run. Five runs are measured
(Section~\ref{sec:lci}). The job is assumed to be executed 100~times per year,
an assumption listed in Section~\ref{sec:threats}.

\emph{Functional unit.} The GWP100 carbon footprint of one execution of
\texttt{kc-py1.py} at commit \texttt{e2574719} of \texttt{lh3/kmer-cnt},
counting exact canonical 31-mers in \texttt{M\_abscessus\_HiSeq\_10M.fa.gz}
(187\,693\,955~bytes, SHA-256 \texttt{dd2ef49a\ldots e736}), submitted by a
student user on Aion, partition \texttt{batch}, holding one exclusive regular
node (2~$\times$~AMD EPYC~7H12, 128~cores, 224\,000~MiB reservable memory) for
a median walltime of 368~s.

\emph{Method.} One criterion: a carbon footprint in CO\textsubscript{2}e.
The characterisation method is IPCC~2021~\cite{ipcc2021} and the indicator is
GWP100.

\emph{Boundary.} Inside the boundary are the node the job holds for its
walltime, and the share of the interconnect, the storage and the site that
serve it. The last three enter through the power usage effectiveness (PUE)
declared in Section~\ref{sec:lci}. Outside the boundary are the author's laptop,
the login node, the network between laptop and cluster, the one-off download of
the input, the development of the code, and every node and job the allocation
does not reserve.

\emph{Life cycle phases.} For the compute node, the study keeps production,
including the extraction of raw materials that cradle-to-gate data contain, and
use. For the interconnect, the storage and the site, it keeps use only, through
the declared PUE. End of life is not inventoried separately: the disposal route
of Aion's hardware is not published. One of the candidate hardware datasets
of Section~\ref{sec:lci} nonetheless includes disposal. That mismatch is listed
in Section~\ref{sec:threats}.

\emph{Components.} The study is capped at four components, which
Section~\ref{sec:lci} inventories in this order:
(1)~the \emph{compute node}: its electricity during the walltime and a share of
its manufacture;
(2)~the \emph{interconnect}: the HDR100 InfiniBand fabric that carries the
job's reads and writes between the node and shared storage;
(3)~the \emph{storage}: the shared GPFS file system that holds the input, the
code and the output;
(4)~the \emph{site}: cooling and power distribution around the machine.

\subsection{Life cycle inventory}\label{sec:lci}
The inventory lists the physical flows the assessment runs on, and how each
was obtained. It holds no grams: those belong to Section~\ref{sec:lcia}. Every
entry is gathered in Table~\ref{tab:inventory} in Appendix~A, with its source
and the date it was read. The raw scheduler records, logs and commands are kept
in the project repository.

\emph{The measurement.} The frozen commit and input of
Section~\ref{sec:goalscope} were run five times as separate batch jobs on
29~September~2026, submitted consecutively with
\texttt{-{}-dependency=singleton} so that no two overlapped. Each run held its
node exclusively, and all five landed on \texttt{aion-0127}. All five completed
with exit code~0 and wrote identical output. All five are kept and the median
is reported. Walltimes were 362, 364, 368, 369 and 372~s: a median of 368~s and
a spread of 10~s from fastest to slowest. File system caches were neither reset
nor measured. The first run is not the slowest (the third is), so these runs
show no first-run effect, but they do not establish whether any run started
cold. The records were read with \texttt{sacct} on 29~September~2026. The
fields read, and why each is the quantity claimed, are:
\texttt{Elapsed}, the time from start to end of the allocation, which is the
walltime the node is held;
\texttt{AllocNodes} and \texttt{AllocCPUS}, the node and cores held;
\texttt{ReqMem}, the memory reserved;
\texttt{MaxRSS} of the Python step, the peak resident memory the program
touched, which agrees with the maximum resident set size that
\texttt{/usr/bin/time -v} reports to within 0.2\,\%;
\texttt{MaxDiskRead} and \texttt{MaxDiskWrite} of the batch and Python steps;
and \texttt{ConsumedEnergy} and \texttt{ConsumedEnergyRaw}.

\emph{Whether an energy figure comes back.} It does not come back from the
scheduler. On 29~September~2026, \texttt{scontrol show config} reported the
energy plugin \texttt{acct\_gather\_energy/rapl}. Nevertheless, both energy fields
were empty for every step of all five jobs, and for a separate interactive
allocation checked the same day. The empty fields are missing data, not zero
energy. The processor's own RAPL counters are readable by an ordinary user
through \texttt{/sys/class/powercap}, while \texttt{perf} reports its package
energy event as not supported. The job was therefore run five more times on
29~September~2026, with the same program, input and allocation. Each run read
both package counters directly before and after the Python step, and corrected
for counter wrap. \texttt{aion-0127} was busy, so these five runs and an idle
reading were moved to \texttt{aion-0144}, an identical regular node. All five
completed with exit code~0 and wrote the same histogram, and Slurm's energy
fields stayed empty. Over Python steps of 357.6 to 366.4~s, the two CPU packages
drew a median of 67\,834~J (range 67\,129 to 68\,827~J), an average of 188~W.
Read the same way for 60~s after the fifth run, the idle node drew 10\,959~J, or
183~W. Assuming that idle rate held throughout each run, the job's activity
adds a median of only 1\,863~J (range 1\,690 to 1\,953~J). So 97\,\% of the
package energy is drawn by a node the job holds but barely uses. RAPL covers
the processor packages only: memory, board, local disk, fans and network card
are outside it, and so is the time the allocation runs outside the Python step.
Because no instrument reaches the whole node, the node's electricity is also
estimated with the Green Algorithms model~\cite{lannelongue2021}:
the walltime times the power of the cores and memory held, using 280~W per
64-core processor~\cite{ulhpcaion} and 0.3725~W per GB of memory. The whole
256~GB installed is counted, because the exclusive allocation holds all of it.
Counting one active core gives 36.7~kJ (0.0102~kWh) per run. Counting all
128~allocated cores at full power gives 241~kJ (0.0670~kWh). The measured
package energy alone, 67.8~kJ, is almost twice the first figure. So the one-core
model understates the node, and both model figures are scenarios, not bounds.
The measured package energy is the figure this inventory carries forward.

\emph{Allocation rule.} Anything shared across many runs is divided down to one
run by the node-seconds the job holds over the node-seconds the hardware
delivers during its service life. For one exclusive node this is the walltime
over the service life. The same rule is applied in every subsection below.

\subsubsection{Compute node}
Operational: 67\,834~J of CPU-package electricity per run (median, RAPL), of
which 1\,863~J is above idle, over a median walltime of 368~s,
holding 1~node and 128~cores. Memory reserved: 224\,000~MiB (\texttt{ReqMem}),
of the 256~GB installed~\cite{ulhpcaion}. Memory touched: 7\,760\,436~KiB, or
7.40~GiB (median \texttt{MaxRSS}). The job therefore touches 3.4\,\% of what it
reserves, and 211~GiB stays reserved but unused.
Embodied: ecoinvent cut-off v3.11~\cite{ecoinvent311} holds no server
production activity. Searches on 29~September~2026 for \emph{server} (58
activities, 32 products), \emph{computer production}, \emph{computer, desktop}
and \emph{computer, laptop} found none. The closest dataset is
\emph{computer production, desktop, without screen} (GLO, 1998--2024,
per unit). It models a 2002 single-processor desktop of 11.3~kg and includes
packaging and disposal. Under IPCC~2021 GWP100 it carries 221~kg
CO\textsubscript{2}e per unit. A two-socket AMD EPYC server, the Dell PowerEdge R7525, has a published production footprint of
1\,768.4~kg CO\textsubscript{2}e, of which 854.7~kg comes from two 4~TB
SSDs~\cite{dellr7525}. That study uses IPCC~2013 rather than IPCC~2021, and its
server differs from an Aion blade. Neither figure describes an Aion node. Which
one enters Section~\ref{sec:lcia}, and why, is decided there. Aion entered
production in October--November 2021 and still runs in September
2026~\cite{ulhpcaion}. No retirement date is published, so a service life of
six years is assumed (Section~\ref{sec:threats}). One run then holds 368~s of
189\,345\,600~node-seconds, a share of $1.94\times10^{-6}$ of the node.

\subsubsection{Interconnect}
The job runs on one node, so no node-to-node traffic occurs. Its only traffic
on the HDR100 fabric (link rate~100, read with \texttt{ibstat}) is file system
I/O. The step counters do not measure storage traffic directly. The Python
step's \texttt{MaxDiskRead} of 680.67~MiB equals the decompressed stream that
\texttt{gzip} writes into the pipe (713\,674\,148~bytes, or 680.61~MiB). The
batch step's \texttt{MaxDiskWrite} of 680.72~MiB is \texttt{gzip} writing that
same pipe. What the batch step reads beyond the pipe, about 198~MiB, is the
179~MiB compressed input plus about 19~MiB of other files, most likely the
loaded modules. The data read from storage per run is therefore about
187\,693\,955~bytes plus about 19~MiB, and the data written is the
1\,972-byte histogram plus the job log. This breakdown is inferred from the
counters, not measured on the fabric. Runs~2 to~5 may have read the input from
the node's page cache. The fabric's energy is not metered per job. It enters
through the declared PUE of the site subsection.

\subsubsection{Storage}
The repository, input and output sit on Aion's shared GPFS file system
(\texttt{df -T}, 29~September~2026)~\cite{ulhpcaion}. Per run, the job keeps
the 187\,693\,955-byte input and writes the 1\,972-byte output, reading and
writing the bytes listed under the interconnect. Storage energy is not metered
per job. It enters through the declared PUE of the site subsection.

\subsubsection{Site}
The University of Luxembourg HPC centre publishes no PUE for Aion. This study
therefore declares 1.36, the EU average PUE for 2023, reported in 2024 and
published in the European Commission's first technical report on data-centre
energy performance~\cite{eudc2025}, read on 29~September~2026. It is a regional proxy,
not a measurement of this site. It multiplies the operational energy of the
compute node, and covers cooling, power distribution, interconnect and storage.
How far a different value would move the result is discussed in
Section~\ref{sec:threats}.

\subsection{Life cycle impact assessment}\label{sec:lcia}
The impact assessment multiplies each inventory flow by a characterisation
factor, an impact per unit of flow, chosen, cited and motivated. This study
assesses one impact category, climate change. It is a single-criterion
carbon footprint in CO\textsubscript{2}e. It leaves out water use, mineral
resource use and every other category of the Environmental Footprint method.
The characterisation method is IPCC~2021~\cite{ipcc2021}, and every factor below
is read as GWP100. The chain from joules to grams is gathered in
Table~\ref{tab:chain} in Appendix~A. Every value in it is recomputed from the
raw records by the script \texttt{lcia-calculation.py} of the project
repository.

\emph{The energy boundary.} The measured CPU-package energy of
Section~\ref{sec:lci}, 67\,834~J, covers the two processor packages during the
Python step only. The job, however, holds the whole node for its walltime.
This study therefore builds a node estimate from three terms, each taken per
run from the five \texttt{aion-0144} runs and paired with those runs' own
timing:
(1)~the measured package energy over the Python step;
(2)~the idle package rate, 182.6~W, over the rest of the allocation, the gap
between Slurm's \texttt{Elapsed} and the Python step (1 to 3~s per run, 0.2 to
0.6~kJ);
(3)~the memory, modelled with the Green Algorithms coefficient of
0.3725~W/GB~\cite{lannelongue2021} for the 256~GB installed, 95.4~W, over
\texttt{Elapsed}.
The median node estimate is 103\,146~J (range 101\,622 to 104\,215~J), or
0.0287~kWh, over a median \texttt{Elapsed} of 364~s. It is still partial. The
board, the local SSD, the network card and power conversion are outside it, and
Section~\ref{sec:threats} gives their likely size. The functional unit's 368~s
comes from the \texttt{aion-0127} series, which carries no energy reading. The
energy chain uses the 364~s of the \texttt{aion-0144} runs instead, so that
energy and time come from the same runs. The two medians differ by 1.1\,\%.

\emph{Site.} The declared PUE of 1.36~\cite{eudc2025} (Section~\ref{sec:lci})
multiplies the node estimate: $0.0287~\text{kWh}\times1.36=0.0390$~kWh drawn
by the site per run.

\emph{Grid factor.} Aion is in Luxembourg. The factor is ecoinvent~3.11 cut-off,
\emph{market for electricity, low voltage}, LU, time period 2020--2024, IPCC~2021
climate change total excluding biogenic CO\textsubscript{2},
GWP100~\cite{ecoinventlu}: 337~gCO\textsubscript{2}e/kWh, read on 19~October
2026. It describes the electricity consumed in Luxembourg, imports and grid
losses included, which is the electricity the site draws. A factor that
counts only generation on national territory would leave out the imports.
Operational impact: $0.0390~\text{kWh}\times337~\text{g/kWh}=13.1$~gCO\textsubscript{2}e
per run.

\emph{Hardware production.} Section~\ref{sec:lci} holds two proxies. This study
uses the Dell PowerEdge R7525~\cite{dellr7525}, a two-socket AMD EPYC
server, because the ecoinvent desktop dataset models a 2002 single-processor
machine of 11.3~kg. The R7525 figure is 1\,768.4~kg CO\textsubscript{2}e, of
which 854.7~kg comes from two 4~TB SSDs. An Aion node holds one 480~GB SSD, so
the two SSDs are removed, which leaves 913.7~kg. The Dell study characterises
with IPCC~2013, not IPCC~2021, and publishes no inventory per gas, so the figure
cannot be recharacterised. For CO\textsubscript{2} the two methods agree, with a
GWP100 of~1 by definition. Between them, the GWP100 of fossil methane moves from
28 to 29.8 and that of N\textsubscript{2}O from 265 to
273~\cite{myhre2013,ipcc2021}, which are changes of 6\,\% and 3\,\%. A change of
that order on the hardware term moves the total by less than 1\,\%. The figure
is therefore kept and labelled IPCC~2013 in Table~\ref{tab:chain}. The grid
factor is not applied to it, because the hardware is made worldwide. With the
allocation rule of Section~\ref{sec:lci} and the 364~s of the paired series, one
run holds $364/189\,345\,600=1.92\times10^{-6}$ of a six-year life, so
$913.7~\text{kg}\times1.92\times10^{-6}=1.76$~gCO\textsubscript{2}e per run.

\emph{Result.} One run of the baseline job emits
$13.1+1.8\approx15$~gCO\textsubscript{2}e, to two significant figures.

\subsection{Interpretation}\label{sec:interpretation}
The figure of 15~gCO\textsubscript{2}e is the GWP100 footprint of one run of
the frozen job holding one exclusive Aion node for 364~s. It counts the
measured CPU packages, a modelled memory, the site through a proxy PUE, and a
time share of a proxy server's production.

\emph{Against daily life.} A 5~W LED bulb lit for one hour draws 5~Wh, or
1.7~gCO\textsubscript{2}e on the same Luxembourg factor. One run therefore
equals about 9~hours of that bulb. It also equals about 50~m in a small petrol
car, at 291~gCO\textsubscript{2}e per km~\cite{ries2026s2}. That figure is
cradle to grave and includes the road, so it has a wider boundary than the
footprint of one run. At the assumed 100~runs per year, the job emits
1.5~kgCO\textsubscript{2}e per year.

\emph{Against the alternative scenarios.} Table~\ref{tab:scenarios} in
Appendix~A puts the chosen estimate next to the energy scenarios of
Section~\ref{sec:lci}, all on the 364~s of the paired series. The Green
Algorithms figures of Section~\ref{sec:lci}, 36.7 and 241~kJ, used the 368~s of
\texttt{aion-0127}, so they are 1.1\,\% higher than the 36.3 and 238.6~kJ shown
here. Each gap has one cause.
The package energy alone, 67.8~kJ, lacks the memory term (34.7~kJ) and, for
the median run, the 0.6~kJ outside the Python step. It is 34\,\% below the chosen figure.
The one-core model, 36.3~kJ, counts 4.4~W of processor power where the
packages measure 188~W, because it gives the 127 unused cores no power at all.
That accounts for its entire 66.8~kJ gap, since the memory term is the same in
both. The all-cores model, 238.6~kJ, counts 560~W of processor power, the
rated maximum of both packages. That is 135~kJ more than the chosen figure.
The package energy above idle, 1.9~kJ, is the work the program itself adds. It
is less than 2\,\% of the chosen figure.

\emph{Which check this is.} The all-cores model is a top-down estimate: the node
held, times its rated processor power, times the walltime. Next to a counter
reading, it tests the reading. The measured 188~W is 34\,\% of the rated
560~W. That ratio is plausible for a node on which one core of 128 works, so
the check supports the reading and does not contradict it. The one-core model is
a substitute. Next to the reading, the substitute is the figure under test:
used on an exclusive node, it understates the processor power 43-fold
(4.4 against 188~W) and the node estimate almost threefold. The chosen result keeps the reading, and uses a model only for the
memory, which no counter reaches.

\subsection{Reporting}\label{sec:reporting}
The baseline is 15~gCO\textsubscript{2}e per run: 13.1~g of electricity and
1.8~g of hardware production. The functional unit is one run of
\texttt{kc-py1.py} on the fixed input, holding one exclusive regular Aion node
on partition \texttt{batch} for 364~s. The conventions are IPCC~2021 GWP100,
CPU packages measured with RAPL over the Python step, memory modelled at
0.3725~W/GB, a PUE of 1.36, a grid factor of 337~gCO\textsubscript{2}e/kWh and
a six-year hardware life. Across the node scenarios of
Table~\ref{tab:scenarios}, the total ranges from 6.4 to 32~gCO\textsubscript{2}e. A reader who reuses the
figure should scale it with the node-time held, not with the CPU work done.

Two hotspots carry the result, and both come from the allocation shape rather
than from the counting. The first is the idle draw of the CPU packages of the
exclusive node: 8.5~gCO\textsubscript{2}e, or 57\,\% of the total with its share
of the site overhead. The program's own work above idle takes 1.6\,\%. The
second is the reserved memory: 4.4~gCO\textsubscript{2}e, or 30\,\%. The job touches
3.4\,\% of that memory. The remaining 12\,\% is hardware production.
Section~\ref{sec:optimisation} attacks these two hotspots: one 128-core node,
held whole, for a program that uses one core and 7.4~GiB.

\section{Threats to Validity}\label{sec:threats}
This section lists the limitations of Section~\ref{sec:lcia} that remain open.
For each, it gives the direction in which it moves the baseline of
15~gCO\textsubscript{2}e and, where possible, by how much. Each shift below
moves one input of \texttt{lcia-calculation.py} and holds the others fixed.

\emph{Missing whole-node power.} No instrument reaches the whole node. RAPL
covers the processor packages only, and the memory term is a generic
coefficient~\cite{lannelongue2021}, not a reading. The board, the local SSD, the
network card and power conversion are not counted, so the result is too low.
Their power on an Aion node is not published. Each 50~W they draw adds
2.3~gCO\textsubscript{2}e per run, or 16\,\%. The memory coefficient can err in
either direction. The idle rate assumed outside the Python step concerns at
most 0.6~kJ per run, under 1\,\% of the node estimate. The idle reading is one
60-second interval taken after the fifth run. If the idle draw varies over time,
the 57\,\% hotspot share moves with it.

\emph{Proxy PUE.} The PUE of 1.36 is an EU average for 2023~\cite{eudc2025}, not
a value measured at this site. Aion's blades are built on a cold plate that cools every component by
direct contact~\cite{ulhpcaion}, which may put the site below the average, but
no site value is published. A PUE of 1.1 gives
12.4~gCO\textsubscript{2}e, 17\,\% less, and 1.6 gives
17.2~gCO\textsubscript{2}e, 16\,\% more. Each step of 0.1 moves the result by
about 1.0~g.

\emph{Grid factor.} The factor describes low-voltage consumption, including
distribution losses. If the site is supplied at a higher voltage, part of those
losses does not apply, and the result is slightly too high. The voltage of the
connection is not published. The factor rests on the 2020--2024 market and
is shown to three significant figures. Its documentation also refers to the
high voltage level, against its own title.

\emph{Proxy hardware data.} No production footprint exists for an Aion node.
The R7525 is a rack server with its own chassis, fans and power supplies. An
Aion node is one of three nodes in a cold-plate-cooled blade~\cite{ulhpcaion}. The SSDs are removed
on the assumption that the rest of the R7525 resembles the node. With the
ecoinvent desktop instead, the hardware term falls to 0.43~g and the total to
13.6~g, 9\,\% less. With the R7525 as published, the hardware term rises to 3.4~g
and the total to 16.5~g, 11\,\% more. The R7525 figure uses IPCC~2013. For
methane and N\textsubscript{2}O this moves the hardware term by a few per cent
and the total by less than 1\,\% (Section~\ref{sec:lcia}). The fluorinated gases
of chip making are not broken down in the Dell study, so their change between
the two methods is not checked. The production of the chassis, the switches,
the storage servers and the building is left out, so the result is too low.

\emph{Assumed service life.} The six-year life is an assumption. Aion has run
for five years and has no published retirement date~\cite{ulhpcaion}. A
four-year life gives 15.8~g, 6\,\% more, and an eight-year life gives 14.4~g,
3\,\% less. The allocation also assumes that the node is available for every
second of its life. Downtime and idle periods between jobs spread production
over fewer node-seconds, so the hardware term is too low by that unknown
fraction.

\emph{Cache state.} File system caches were neither reset nor measured, so a
run may have read its input from the page cache rather than from GPFS. The
Python step is bound by computation: its CPU time is 99.7\,\% of its elapsed
time in job 15861652. Reading from storage is therefore a small part of the
walltime. The walltimes of the five paired runs span 359 to 368~s, and the node
estimate spans 101.6 to 104.2~kJ. A cache effect is bounded by that 2.5\,\%
spread.

\emph{Measurement on different nodes.} The walltimes of the functional unit come
from \texttt{aion-0127}, and the energy from \texttt{aion-0144}. The chain uses
only the \texttt{aion-0144} values. With the 368~s of \texttt{aion-0127}, the
result would be 15.05 instead of 14.89~gCO\textsubscript{2}e, 1.1\,\% more. An
idle package reading on a third node, \texttt{aion-0234}, gave 178.6~W against
182.6~W on \texttt{aion-0144}. Identical nodes thus differ by about 2\,\% at
idle.

\emph{Figures with different boundaries.} The electricity terms cover use only.
The R7525 figure covers production, while the ecoinvent desktop includes
packaging and disposal. End of life is outside the result, so the result is too
low by the unknown share of disposal. The car comparator of
Section~\ref{sec:interpretation} is cradle to grave, which makes one run look
smaller next to it than a comparison on the same boundary would.

\emph{Runs per year.} The figure of 100~runs per year is an assumption. It
leaves the result per run unchanged and scales only the annual figure and the
payback period of Section~\ref{sec:payback}.

\emph{One criterion, burden shifting.} The result covers climate change only, on
one job. It hides the mineral and water use of hardware production. A change
that frees the node may also lead the job to be run more often. The result
supports no comparison with another job.
